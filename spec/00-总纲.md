## 1. 本规范的地位

| 项 | 说明 |
|----|------|
| 覆盖范围 | 交易、区块、收据、状态、共识消息五类结构的**每一个字节** |
| 不覆盖 | 网络传输分帧（由 libp2p 负责）、RPC 的 JSON 编码（另行定义） |
| 一致性要求 | 任何语言照本规范实现，必须产生**逐字节相同**的输出 |
| 变更流程 | 变更需新增 ADR 并递增 `SCHEMA_VERSION`，不得静默修改 |

## 2. 全局约定

### 2.1 字节序

**一切多字节整数统一使用大端（big-endian / network byte order）。**

理由：大端编码的字节字典序 = 数值序，使存储层可以直接用字节序做范围扫描与排序。
这是最容易被忽略、后期最难改的设计决定。

唯一的例外是智能合约内部的 EVM 语义（EVM 自身规定），与本规范无关。

### 2.2 长度前缀

| 类型 | 编码 |
|------|------|
| 定长字节数组（`BytesN`） | 原样 N 字节，**无长度前缀** |
| 变长字节序列（`Bytes`） | SSZ 可变长：4 字节小端长度前缀（offset 机制，见 01 章） |
| 定长列表 | 元素直接串联 |
| 变长列表 | SSZ offset 机制（见 01 章） |

### 2.3 整数类型

| 名称 | 长度 | 范围 | 备注 |
|------|------|------|------|
| `uint8` | 1 | 0–255 | |
| `uint16` | 2 | | 大端 |
| `uint32` | 4 | | 大端 |
| `uint64` | 8 | | 大端，用于 Height / Nonce / Gas |
| `uint256` | 32 | | 大端，用于 Wei（金额） |

**禁止使用有符号整数表示金额、高度、gas、nonce。**
**禁止使用浮点数**（IEEE 754 在不同平台/优化级别可能有 1 ULP 差异 → 分叉）。

### 2.4 比率表示

所有比率用**基点（basis points, bps）**：`1 bps = 1/10000`。
例：法定人数 66.67% 表示为 `uint16(6667)`。
**禁止** `0.6667` 这类浮点表示。

### 2.5 哈希函数

| 用途 | 函数 |
|------|------|
| 通用哈希 / 地址派生 | **Keccak-256**（注意：不是 SHA3-256，Keccak 的 padding 不同） |
| SSZ 哈希树根 | SHA-256（遵循 SSZ 规范） |
| Merkle 树内部节点拼接 | Keccak-256 |

### 2.6 签名

| 用途 | 算法 | 签名长度 |
|------|------|---------|
| 交易签名 | secp256k1（EIP-155，含 chainId 防重放） | 65 字节（r‖s‖v） |
| 共识投票 | secp256k1 | 65 字节 |
| 验证者身份密钥 | Ed25519（可选） | 64 字节（v0 不用） |

签名覆盖的内容**必须包含 domain tag**（用途标签），防止跨用途/跨链重放。

## 5. 测试向量约定

每份规范配套 `vectors/*.json`，格式为：

```json
{
  "name": "simple_transfer",
  "description": "一笔最简单的 EIP-1559 转账",
  "input": { "...": "规范中定义的结构，十六进制字符串表示字节" },
  "expected": {
    "encoding": "0x...",
    "hash": "0x..."
  }
}
```

规则：
- 所有字节字段用 **`0x` 前缀的十六进制字符串**表示
- 所有整数字段用**十进制字符串**表示（避免 JSON number 精度问题）
- 测试向量文件是规范的一部分，与规范同版本

## 6. 确定性要求（贯穿全部章节）

任何参与**哈希、状态根、共识**的计算必须满足：

1. 不依赖 `time.Now()` —— 时间只能来自区块头（由共识规则约束）
2. 不依赖 `math/rand` —— 随机只能来自确定性派生
3. 不使用浮点
4. 集合遍历顺序**显式定义**（禁止依赖语言/库的默认顺序）
   —— Go 的 `map` 遍历顺序是随机的，**实现时必须显式排序**
5. 不依赖 locale、时区、平台默认编码

违反任一条都会导致链分叉。
