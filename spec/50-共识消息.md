# 50 · 共识消息

> Tendermint 式三阶段 BFT。本文定义线上传输与签名覆盖的字节格式。

---

## 1. 消息信封

```
message = msg_type(1) ‖ payload
```

| `msg_type` | 名称 | 说明 |
|-----------|------|------|
| `0x01` | `Proposal` | 提议区块 |
| `0x02` | `Prevote` | 预投票 |
| `0x03` | `Precommit` | 预提交 |
| `0x04` | `Status` | 链高度探测 |
| `0x05` | `BlockRequest` | 区块同步请求 |
| `0x06` | `BlockResponse` | 区块同步响应 |
| `0x07` | `Evidence` | 罚没证据广播 |

---

## 2. Proposal

| # | 字段 | 类型 | 说明 |
|---|------|------|------|
| 0 | `height` | uint64 | |
| 1 | `round` | uint32 | |
| 2 | `pol_round` | int32 | `-1` = 无 POL；否则为获得 POL 的轮次 |
| 3 | `block` | Block | 完整区块（见 20 章） |
| 4 | `proposer` | Address | |
| 5 | `signature` | Bytes65 | secp256k1 |

### 签名覆盖（domain separation）

```
domain = keccak256("chfault/Proposal/v1" ‖ chain_id(8BE))
digest = keccak256(domain ‖ height(8BE) ‖ round(4BE) ‖ block_hash(32))
signature = secp256k1_sign(digest, proposer_key)
```

**必须包含 chain_id**，防止跨链重放。
**必须包含 domain tag**，防止把 Prevote 签名当 Proposal 用。

## 3. Vote（Prevote / Precommit 共用）

| # | 字段 | 类型 | 说明 |
|---|------|------|------|
| 0 | `height` | uint64 | |
| 1 | `round` | uint32 | |
| 2 | `block_hash` | Bytes32 | nil 票用 32 字节零 |
| 3 | `is_nil` | bool | true 表示投 nil |
| 4 | `validator` | Address | 投票者 |
| 5 | `signature` | Bytes65 | |

### 签名覆盖

```
domain = keccak256("chfault/Prevote/v1" ‖ chain_id)     // 或 Precommit
digest = keccak256(domain ‖ height(8BE) ‖ round(4BE) ‖ block_hash ‖ is_nil)
```

**Prevote 与 Precommit 用不同的 domain tag** —— 否则同一轮次的签名可被跨类型复用。

## 4. QuorumCertificate (QC)

| # | 字段 | 类型 | 说明 |
|---|------|------|------|
| 0 | `height` | uint64 | |
| 1 | `round` | uint32 | |
| 2 | `block_hash` | Bytes32 | |
| 3 | `signers` | Bitmask | 位图，第 i 位 = 验证者集第 i 个成员 |
| 4 | `signature` | Bytes \| null | v0 = null（逐个验签）；v2 = BLS 聚合签名 |

### 4.1 位图编码

```
bitmask_len = ceil(validator_count / 8) 字节
第 i 个验证者 → 字节 i/8 的第 (i % 8) 位（从 LSB 计）
```

**验证者集顺序**：按 `Address` 字节序升序排列（确定性，见 01 章 §8）。
**这个顺序必须固定**，否则位图语义在不同节点会不一致 → 分叉。

### 4.2 v0 的验签方式

`signature == null` 时，QC 携带的是**逐个签名列表**（存在 `signers` 对应的独立结构里，
v0 简化为：QC 附带 `[]Vote`，位图仅用于快速去重）。

**明确**：v0 **不做签名聚合**（ADR-009）。`signature` 字段**现在就存在**，
v2 启用 BLS 时上层代码不需要改结构 —— 这就是"接口预留"。

### 4.3 阈值校验

```
signed_power = Σ power[i] for i where bitmask[i] == 1
require signed_power * 3 > total_power * 2     // 严格超过 2/3
```

**用整数乘法比较，不要用浮点除法**。
`> 2/3` 而非 `>= 2/3`，这是 BFT 安全性的要求。

## 5. Evidence（双签证据）

| # | 字段 | 类型 | 说明 |
|---|------|------|------|
| 0 | `kind` | uint8 | `1` = 双 prevote，`2` = 双 propose |
| 1 | `height` | uint64 | |
| 2 | `round` | uint32 | |
| 3 | `validator` | Address | 作恶者 |
| 4 | `a` | SignedVote \| SignedProposal | 第一个签名消息 |
| 5 | `b` | SignedVote \| SignedProposal | 第二个签名消息 |

### 有效性条件

1. `a` 与 `b` 的 `(height, round, validator)` 相同
2. `a` 与 `b` 的内容不同（不同 block_hash，或不同 block）
3. 两个签名都有效
4. 签名者确实是当时的活跃验证者

满足 → 该验证者 `jailed_until = height + JAIL_BLOCKS`（默认 10000）。

## 7. 网络主题（libp2p GossipSub）

| 主题 | 内容 |
|------|------|
| `/chfault/<chain_id>/tx/1` | 交易广播 |
| `/chfault/<chain_id>/block/1` | 已最终化区块 |
| `/chfault/<chain_id>/consensus/1` | 共识消息（Proposal/Vote） |

**`chain_id` 进主题名**：同一物理网络跑多条链时不会串扰（测试环境常见需求）。

请求响应用独立协议：
- `/chfault/<chain_id>/status/1.0.0`
- `/chfault/<chain_id>/sync/1.0.0`

## 8. 消息大小限制

| 项 | 上限 |
|----|------|
| 单条消息 | 2 MiB |
| Proposal（含区块） | 受 `MAX_BLOCK_SIZE` 约束 |
| Vote | 固定，约 110 字节 |
| 每 peer 速率 | ≤ 500 msg/s |

---

## 9. 确定性要求

共识消息的**处理顺序**由单 goroutine 事件循环保证（见 `docs/blueprint/02` 2.4）。

**禁止**：
- 用 `map` 遍历顺序决定投票统计顺序
- 用 goroutine 并发修改共识状态

**必须**：
- 验证者集按 `Address` 升序排序后使用
- 投票统计用确定性顺序（按验证者索引，而非 map 迭代）
